# 知识库 Schema — 编译规范与判断规则

> **版本**: v1.0
> **说明**: 本文件是知识库管理师的工作手册。所有判断规则、编译规范、程序验证规则均在此定义。
> **权限**: 用户独占写入。知识库管理师仅在用户显式指令时可修改。

---

## 一、编译规范

### 1.1 整体结构

知识单元必须包含以下 7 个段落（按顺序）：

1. **一句话摘要**：扫一眼就知道讲什么（1-2 句话）
2. **核心要点速览表**：| 重点知识 | 关键数据/结论 |（不展开细节）
3. **详细内容**：按维度完整展开，不照搬来源原文，用自己的话重组
4. **未解决线索（Open Threads）**：只列**活跃的**待验证/待补充线索
5. **相关知识单元**：[[主题名]] — 关系说明
6. **更新日志（Timeline）**：操作历史 + 来源记录
7. **来源标注**：章节/主题级标注，非语句级

### 1.2 编译原则

- ✅ 理解后用自己的语言重新组织，不照搬原文
- ✅ 一个主题一个知识单元（粗粒度）
- ✅ frontmatter 与正文联动决策（不可割裂）
- ❌ 语句级来源归因（LLM 不可靠）
- ❌ 照搬来源原文（不是简单复制粘贴）
- ❌ 保留与主题无关的信息

### 1.3 知识单元命名规范

| 规则 | 说明 | 示例 |
|------|------|------|
| 使用主题名 | 直接用知识单元的主题名作为文件名 | `微服务架构.md`、`API设计规范.md` |
| 简洁明了 | 2-6 个字为宜，避免过长 | `RAG技术.md` 而非 `检索增强生成技术详解.md` |
| 中文优先 | 中文内容用中文命名 | `项目验收.md` |
| 避免特殊字符 | 不用 `/`、`\`、`:` 等 | 用空格或连字符分隔 |

## 二、判断规则卡

### 2.1 domain 判断规则

**定义**：知识单元所属的领域/范畴。

**判断规则**：
- 根据内容主题推断所属 domain
- 优先匹配已知 domain 列表（见 RESOLVER 路由参考）
- 不在已知列表中 → 标注"domain 待确认"，并在 RESOLVER 中记录

**示例**：

| 内容示例 | 判断 | 理由 |
|---------|------|------|
| 项目验收流程 | 项目管理 | 属于项目生命周期 |
| Python 装饰器用法 | 编程技术 | 属于技术实现 |
| 供应商选择策略 | 供应链管理 | 属于采购领域 |

**不确定时**：标注"domain 待确认"，让用户审核时决定。

---

### 2.2 tags 判断规则

**定义**：知识单元的关键词标签，用于快速筛选。

**判断规则**：
- 短词优先（1-3 个汉字或 1-2 个英文单词）
- 不使用组合词（如"验收流程管理"应拆为"验收"+"流程"）
- 中英文不混用（同一 tag 内不混合中英文）
- 从内容中提取 2-5 个最具代表性的关键词

**示例**：

| 内容示例 | ✅ 正确 tags | ❌ 错误 tags |
|---------|-------------|-------------|
| 项目验收流程管理 | [验收, 流程, 项目, checklist] | [验收流程管理, 验收checklist] |
| Python 异步编程 | [Python, 异步, async] | [Python异步, asyncio用法] |

**格式校验（Harness）**：tag 不含空格、不含特殊字符、不含中英混用。

---

### 2.3 aliases 判断规则

**定义**：知识单元的别称/同义词，用于多路径匹配。

**判断规则（三步流程）**：
1. **语义识别**：分析来源内容，判断是否存在已有知识单元的别称 → 确定则直接关联
2. **联网搜索**（如 tavily_search 可用）：不确定 → 搜索验证 → 确定则关联
3. **标注待验证**：仍不确定 → 标注 aliases_pending，等待用户审核

**示例**：

| 已有主题 | 来源中出现 | 判断 | 操作 |
|---------|-----------|------|------|
| 项目验收 | "验收流程" | 语义相近 | aliases 添加"验收流程" |
| Karpathy | "Karpathy方法" | 可能相关 | 联网搜索 → 关联 |
| 知识编译 | "LLM Wiki" | 不确定 | aliases_pending |

**格式校验（Harness）**：aliases 为数组，每个元素为字符串。

---

### 2.4 freshness 判断规则

**定义**：知识单元的时效性特征。

**判断规则（三分法）**：
- 内容含有时效信号（如"2025年""最新""当前"） → `time-sensitive`
- 内容明确永恒不朽（如"勾股定理""Git 基本原理"） → `enduring`
- **模棱两可 → 默认 `time-sensitive`**（宁可保守）

**示例**：

| 内容示例 | 判断 | 理由 |
|---------|------|------|
| "2025年行业验收标准" | time-sensitive | 明确时间信号 |
| "勾股定理" | enduring | 数学定理，永恒不变 |
| "Git 常用命令" | time-sensitive（默认） | 命令可能更新 |

**不确定时**：默认 `time-sensitive`。用户可在审核时改为 `enduring`。

---

### 2.5 open_threads 判断规则

**定义**：知识单元中尚未解决的线索/疑问。

**三种类型**：
1. **待验证**：信息来自单一来源，未经交叉验证
2. **缺数据**：已知存在但尚未获取的数据/信息
3. **矛盾未解**：不同来源之间存在矛盾，尚未解决

**判断规则**：
- 仅列**活跃的** Open Threads
- 已解决的从列表中移除
- 每条格式：`- [ ] [类型] [描述]`

**示例**：

| 情况 | Open Thread | 类型 |
|------|------------|------|
| 只有一个来源提到"行业标准为XX" | "- [ ] 待验证：行业标准XX是否准确" | 待验证 |
| 知道有但未获取的数据 | "- [ ] 缺数据：2025年验收通过率" | 缺数据 |
| 两个来源对同一事实说法不同 | "- [ ] 矛盾未解：来源A说XX，来源B说YY" | 矛盾未解 |

---

### 2.6 替代型/累积型判断规则

**定义**：来源文件之间的数据关系类型。

**判断规则**：
- **替代型**：新来源中，旧数据失去参考价值，被新数据取代
- **累积型**：新旧来源的数据共存，互为补充

**示例**：

| 来源A | 来源B | 判断 | 理由 |
|------|------|:----:|------|
| 2024验收标准 | 2025验收标准 | 替代型 | 旧标准被新标准取代 |
| 验收流程文档 | 验收案例分析 | 累积型 | 流程+案例互补 |

---

### 2.7 confidence 判断规则

**定义**：知识单元的可信度。

**判断规则**（值域对齐 v3.7 §3.5：stable / unstable / orphan）：
- 来源充足、内容无矛盾 → `stable`
- 来源单一、信息不完整 → `unstable`
- 无任何来源支撑 → `orphan`

**默认值**：新编译的单元默认为 `stable`（除非明显问题）。

---

### 2.8 Open Threads 生命周期

| 状态 | 说明 | 操作 |
|------|------|------|
| **创建** | LLM 在 Ingest 编译时读取来源，发现待验证/缺数据/矛盾未解的线索 | 写入 Open Threads 段落，frontmatter `open_threads_count` 计入 |
| **活跃** | 线索在 Open Threads 段落中 | frontmatter `open_threads_count` 计入 |
| **已解决** | 线索验证完毕 → 移入 Timeline | `open_threads_count` 减 1，Timeline 追加解决证据 |
| **长期未解决** | Lint 检查时提醒 | 通知用户关注 |

**注意**：Open Threads 是 LLM 在编译时基于来源内容的判断（"已知的未知"），不是 Agent 自动扫描知识库发现的（"未知的未知"）。

## 三、后置程序验证规则（Harness，9 条）

以下 9 条规则**不可跳过**，每次编译后必须逐条验证：

| # | 规则 | 检查方式 |
|:-:|------|---------|
| 1 | frontmatter 字段完整性（8 个必填字段：domain, tags, aliases, sources_count, confidence, last_ingested, freshness, open_threads_count） | 逐字段检查 |
| 2 | frontmatter 值合法性（枚举值：domain/confidence/freshness 在合法值范围内） | 枚举匹配 |
| 3 | sources_count == 正文"来源"段落的条目数 | 计数对比 |
| 4 | open_threads_count == 正文"未解决线索"段落的条目数 | 计数对比 |
| 5 | 正文必须包含"一句话摘要"和"核心要点速览"段落 | 文本匹配 |
| 6 | 正文必须包含"详细内容"和"更新日志（Timeline）"段落 | 文本匹配 |
| 7 | （更新场景）对比新旧 frontmatter，标注变更字段 | diff 对比 |
| 8 | （更新场景）domain 变更时，须在 log.md 中说明变更理由 | 文本检查 |
| 9 | （别称场景）aliases_pending 存在时，在输出中明确提醒用户审核 | 字段检查 |

## 四、关联链接规则

- Ingest 时**必须先**读取 index.md 获取已有知识单元列表（含 aliases）
- 根据内容相关性添加 [[主题名]] 双链
- **不强制关联** — 没有相关的就不加
- 格式：`[[主题名]] — 关系说明`
- 正文中的别称自动链接到规范主题名：`[[规范主题名]]`

## 六、Git 提交规范

| 操作 | Commit 格式 | 说明 |
|------|-----------|------|
| 初始化 | `init: 知识库框架初始化` | 首次初始化 |
| Ingest 新增 | `ingest: 新增 [主题名]` | 审核通过后 |
| Ingest 更新 | `ingest: 更新 [主题名]` | 审核通过后 |
| Delete | `delete: 删除来源 [文件名]，重新编译 [知识单元名称]` | 处理后 |
| Lint 修复 | `lint: 修复 [问题描述]` | 用户确认后 |
| Schema 修改 | `schema: 更新 [描述]` | 用户确认后 |
| 手动指示 | `manual: [用户描述]` | 用户手动指示的变更 |

**核心设计：草稿不入 Git 主分支。只有审核通过后的内容才 commit。**
